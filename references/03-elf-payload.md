# 载荷层 — 加密 ELF 的算法无关拆解（L0→L6）

> **加密只改变"数据长什么样"，不改变"数据在哪一层、谁在解它、解给谁用"。**
> 所以不管它是 AES-CBC、XOR 链、RC4、自研位流还是 VM 字节码——判定、定位、取证、找破解点的动作**完全一样**。
> 从上往下走 L0→L6，每层只回答一个问题；卡住时跳到 §14「三条核心」。

配套脚本：`scripts\elfprobe.py`（形态判型）、`scripts\payload.py`（载体链剥离）。

---

## L0 · 先分层，再谈技术

Android 黑产包（外挂/远控/批量注册/挖矿）几乎都是**三层**，层与层保护强度差一个数量级：

```
控制面  APK / dex / Kotlin        ← 最弱：类名和字符串往往明文；负责授权、更新、分发
载荷面  ELF / .so / dump 镜像      ← 最强：加密 + 混淆 + 反调试；负责真正的活
特权面  内核模块 / root 脚本       ← 最隐蔽：按内核/系统版本分发；负责拿到不该有的权限
```

**换任何样本都成立的分工规律**：
- **控制面永远知道载荷面在哪、叫什么、什么时候起。** 所有"我要下什么/起什么/校验什么"的字符串都在这一层。
- **载荷面的名字往往在控制面里写死。** 顺着找。
- **特权面的数量 = 适配矩阵。** 有多少份就说明覆盖多少个内核/系统版本。

> **最常见的开局错误**：拿到一个 16MB 的 `.sh` 直接上 IDA 啃。
> 正解是**先花 20 分钟拆控制面**，让它告诉你这个文件是什么、被谁拉起、需要哪些同伴。

## L1 · 不信扩展名（30 秒，收益极高）

```powershell
python scripts\elfprobe.py "小糊涂破解.和平.VS漏打追锁.sh"
```

```
head=7f 45 4c 46 02 01 01 00  → ELF=True   shell=False
ELF ELF64 LE type=DYN(PIE/so) machine=AARCH64 entry=0x308a9a0 phnum=12 shnum=4
```

| 头 | 真身 | 常见伪装 |
|---|---|---|
| `7f 45 4c 46` | ELF | `.sh` `.bin` `.dat` `.png` |
| `50 4b 03 04` | ZIP/APK/JAR | `.png` `.dat` `.so` |
| `64 65 78 0a` | DEX | `.bin` |
| `1f 8b 08` | gzip | 任何 |
| `fd 37 7a 58 5a` | xz | 任何 |
| `42 5a 68` | bzip2 | 任何 |

三个真实账单：
- VS：`小糊涂…VS漏打追锁.sh`（16.7MB）→ **ELF64 AArch64 可执行文件**，不是脚本。
- 纽约：`纽约1004.sh`（51MB）→ ELF，`e_type=03(DYN)`。
- 小熊维尼：`小熊维尼_8.2.sh` → **真的是 shell 头**（280B）+ gzip + 68MB ELF。同批产品外层形态都不一样。

ELF 再读两个字段：`e_type`（0x10）`01=REL(.ko)` `02=EXEC` `03=DYN(PIE/so)`；`e_machine`（0x12）`B7=AArch64`。
`03` 意味着"需要重定位"—— dump 出来的指针可能是残的。

## L2 · 载体链反推：让控制面告诉你还缺什么

这是全流程里**最省时间**的一步。**做法：把控制面的所有字符串倒出来，只搜"我要拿什么"这类词。**

```python
KW = ['驱动','driver','主程序','main','核心','core','载荷','payload',
      '下载','download','版本','variant','解压','校验','insufficient','缺失']
```

实测捞出来的原话（APK 资源串，明文）：

```
内核驱动模块
仅显示与当前设备内核版本（%1$s）匹配的驱动
发现驱动目录 %1$s（%2$s），下载整包后可按内核版本刷入
驱动包解压失败 / 驱动包大小校验失败 / 驱动文件写入失败
主程序启动器 / 主程序启动失败（exit code: %1$s）
主程序启动成功后自动打开和平精英并退出本应用
主程序退出后按策略清理执行残留
```

七行给出整张工程图，**一行代码都没读**：存在"驱动整包"（按内核版本切分）、存在"主程序"（被 nohup 起、会退出、要清理）、存在 `variant`（主程序不止一份）、有一整套校验（载荷不是随便能替换的）。

> **换任何样本都成立**：分发式样本一定会在客户端留下"它要下什么"的字面描述。
> 这些字面描述**几乎从不加密**——因为产品经理要改文案，文案走资源表，资源表不进加密区。

**反过来也成立（判"缺件"）**：逆 ELF 逆到"它要读一个不存在的东西"，先别怀疑自己——
回控制面找，那个东西很可能是**另一层**，你还没拿到。

## L3 · 「是不是加密载荷」三问（只看 ELF 结构）

### 问 1：它还能不能当正常程序跑？

```python
has_interp  = '.interp' in sections           # 有 /system/bin/linker64 吗
has_dynamic = any(s.type == 'DYNAMIC')        # 有 .dynamic 吗
has_imports = count(sym.shndx == 0)           # 有未定义符号(依赖 libc)吗
```

| 结果 | 判读 |
|---|---|
| interp + dynamic + imports 都有 | 正常动态链接程序（可以运行时下手） |
| 全都没有，只有 2 个 LOAD | **不是给系统加载器用的** → 自建加载器/内核加载，载荷面 |
| dynamic 有但 imports 极少（十几条） | 壳的自举 stub |

实测（VS 32 份驱动载荷，`elfprobe.py` 输出）：

```
type=DYN(PIE/so) entry=0x16091c phnum=4 shnum=0
interp=None  dynamic=False  imports=0
  LOAD off=0x0 vaddr=0x0      filesz=4096  memsz=1014784 exec=False
  LOAD off=0x0 vaddr=0x100000 filesz=398365 memsz=398365 exec=True
```

**这种 ELF 在用户态根本无法成为进程** —— 没有 libc、没有加载器。这一条就把"用户态工具"排掉了。

### 问 2：熵落在哪个区间？

| 熵（4KB–64KB 窗） | 典型内容 |
|---|---|
| < 4.0 | 头/表/零填充 |
| 5.5 – 7.2 | 编译后的代码（AArch64 正常值 6.2–6.8） |
| 7.7 – 8.0 | 加密或压缩 |
| ≈ 7.99 且 16 字节块零重复 | **强加密** |

> 熵只是筛子不是结论：混淆过的代码也会被抬到 7.5+；熵 6.5 也可能是"每 4 字节翻转一位"的轻量加密。

### 问 3：入口在哪？

```
entry 落在 RX 段的头部    → 正常程序
entry 落在 RX 段的尾部    → 解码器 stub 的强信号（数据在前，代码在后）
entry 落在 memsz>filesz 的 bss 区 → dump 残缺 / 运行期填充（静态到此为止）
```

实测：RX 段 `[0x100000, 0x1613e5)`，`e_entry=0x16091c`，**距段尾 2817 字节（=0xB01）**。
这个位置关系几乎只有一种解释：**前面是压缩体，尾部是解码器**。

> 三问合起来，**一次都不用读指令**，就能给出：这是加密载荷、有一个自解密 stub、不依赖 libc。

## L4 · 定位解码器：认骨架，不认算法

### 4.1 标准压缩流先扫一遍（便宜，5 分钟）

```python
for off in range(len(d)-13):
    if d[off]==0x5D and d[off+1:off+5] in (b'\x00\x00\x80\x00', b'\x00\x00\x00\x01'):
        try: lzma.decompress(d[off:], format=lzma.FORMAT_ALONE)
# 同样扫 xz(\xfd7zXZ\x00) / zlib(78 01|5E|9C|DA) / gzip(1f8b08) / bz2(BZh)
```

`payload.py` 已内置这五种 + 递归。**全 0 命中不是死路，是一条信息**：它不用标准压缩 → 要么加密，要么自研位流。

### 4.2 LZ 家族的骨架（三件套）

不管谁写的 LZ 变体，解码循环一定由这三块拼起来：

```asm
; ① 位流读取：函数返回一个 bit，用标志位带出来
BL  get_bit
B.CS  literal_path          ; 借 CF 分支
ADC W1, W1, W1              ; 借 CF 做 n = n*2 + bit

; ② 变长整数（gamma / exp-Golomb / Elias）
loop: BL get_bit ; ADC W1,W1,W1 ; BL get_bit ; B.CC loop

; ③ 回引拷贝：从输出区往回退 offset 字节，逐字节拷
ADD  X3, X2, W1, UXTW
LDURB W3, [X3,#-1]          ; dst[-offset]
STRB W3, [X2],#1            ; *dst++ = ...
SUBS W1, W1, #1
B.NE copy_loop
```

> **看到"读位 → 带进位分支 → 回引拷贝"这三块，就是 LZ 家族**（可能是 NRV2B / LZ4 / aplib / 自研 gamma 编码），**但骨架一定在**。
> 找到骨架就能自己写解码器；找不到骨架才需要去猜算法。

### 4.3 两条「别硬啃」的止损线

- 位流解码器重写 > 2 小时，且**你没有能跑它的机器** → 停，先出定性结论。
- 解码器的输入指针是运行期算出来的（不在文件里）→ 静态拿不到明文，必须动态。

## L5 · 自解密 stub 的四指纹（本页最该记住的一节）

| # | 指纹 | 为什么必然出现 | 怎么看 |
|---|---|---|---|
| 1 | **入口在 RX 段尾部** | 数据在前、代码在后，才能在原地解自己 | `e_entry` vs PH 的 `vaddr+filesz` |
| 2 | **`DC CVAU` / `IC IVAU` 缓存维护** | 改了指令内存就必须刷 I-cache，否则执行旧字节 | 精确编码 `0xD50B7B20` / `0xD50B7520`（capstone 实测） |
| 3 | **写内存 → 跳内存** | 解密完必须跳到刚写过的那片 | 找「ST* 之后 BR/BLR 到同一页」 |
| 4 | **解密循环与被解密区不重叠** | 否则会踩掉自己 | 比较读取指针与写入指针区间 |

```
RX 段 [0x110000,0x178E65)  entry 0x178364          ← 指纹1（距段尾 0xB01）
DC CVAU X2 / IC IVAU X0 / DSB ISH / ISB             ← 指纹2（刷 4KB 对齐范围）
SUB X0, X0, X7 ; STRB W2,[X4] ... 然后跳            ← 指纹3
```

`elfprobe.py` 会直接给出这四项的计数：

```
AArch64 指令面: DC_CVAU=1 IC_IVAU=1 DSB=59 ISB=1 BR=5374 BLR=55 ADRP=150266 …  (xref/MB=3736.5)
```

> 摘壳的动作永远一样：**找到"解完之后跳到哪"，在那里下断，让程序自己解。**
> 算法是它的事，位置是你的事。

## L6 · 分发粒度反推保护形态（5 秒）

| 分发粒度 | 保护形态 | 必然推论 |
|---|---|---|
| 按 `uname -r` 逐内核版本各一份 | 内核态载荷 / 内核内加载 | 无 libc、无符号解析、不依赖动态链接 |
| 按游戏版本各一份 | 用户态外挂 | 硬编码结构体偏移 |
| 一份走天下 | 用户态 + 运行时特征扫描 | 有 pattern 扫描逻辑 |
| 按 GPU 型号 | 图形/渲染层 hook | 有 GL/Vulkan 适配 |
| 按 ROM 厂商（ColorOS/oneplus/MIUI） | 系统服务/框架层改写 | 有厂商私有 API 适配 |

实测 `驱动.zip` 的文件名就是 `uname -r` 前缀：

```
4.9.186 4.14.117 4.14.141 4.14.180 4.14.186 4.19.81 4.19.109 4.19.157 4.19.191
4.19.157-ColorOS 4.19.191-ColorOS 5.4.210-ColorOS 5.4.233-ColorOS
5.4.191oneplus 5.4.233oneplus 5.4.61 5.4.86 5.4.147 5.10 5.15 6.1 6.6 6.12 6.18
```

→ 32 份、覆盖 4.9→6.18、专门做 ColorOS / oneplus 分支。两个推论直接省掉整轮分析：
① 内核版本耦合这么细 → 载荷里**没有**运行时符号解析逻辑，不可能在用户态跑；
② 专门做 ROM 分支 → 一定有"按 ROM 改配置"的控制面逻辑（回 APK 一搜，果然有 `OplusConfigViewModel` / `/data/data/com.oplus.cosa`）。

## §9 · 静态读不出字符串 ≠ 没信息

混淆会加密业务串，但**三类东西几乎不会被加密**——因为它们不是"业务逻辑"，是"别人的东西"：

| 类别 | 例子 | 能反推出什么 |
|---|---|---|
| 静态链接进来的第三方库调试串 | `physx::Sc::Scene::…`、`Gu::ConvexMesh::…` | 它用了什么引擎/中间件 → 要接哪个游戏/框架 |
| 字体/图像/编码表/词典 | `FONTBOUNDINGBOX`、`STARTCHAR`、`Font Awesome 6`、CJK 字形表 | 它要**画字** → 有 UI 浮层；画什么语言 → 面向谁 |
| 数据表 | `名称-类别-ID` 形式的字典 | 它的功能清单 |

实测 VS 主程序 16.7MB、9MB 代码、业务串全加密，看起来是黑箱。但：
- `.rodata` 里躺着整片 `D:\Project\PhysX-4.1\physx\source\...` → 拖了 UE4 物理/数学库 → 要算 3D 坐标；
- `FONTBOUNDINGBOX` + `STARTCHAR` + `Font Awesome 6` → 自带 BDF 字形和图标字体 → **要在没有 Java 的环境里自己画中文 UI**；
- 导入表 `eglCreateWindowSurface / glUniformMatrix4fv / ANativeWindow_*` → 结论闭环：**native 自绘浮层**。

> **通用判据：混淆器不会去改链接器塞进来的东西。**
> 找不到业务串时，去看"谁的东西被链进来了"——那是一张不会说谎的清单。

## §10 · 数据表是情报（最容易被跳过）

一个写着 `名称-ID` 的表，价值超过半个 `.text`。实测 VS 主程序 `.data`：

```
武器挂件——Mk14-阎梦青缨-801101
武器挂件——MG3-梦幻舞会-801102
8倍 瞄准镜-插件提供-9855034
留言信笺-9856001
```

`名称-类别-ID`，**49,110 条**，ID 1000 → 980003003。分类：套装 1517 / M416 1001 / 背包挂件 633 …

直接读出三件事：① 功能（把游戏物品 ID 翻译成人话再画到屏幕上 → 物资/皮肤透视）；
② 覆盖度（49K 条说明从游戏资源批量抽，作者有自动化提取工具链）；③ 版本锚点（ID 上限可反推适配的游戏版本）。

> **一个踩过的坑**：一开始以为 `PASS-801138` 是卡密。核对后发现 `PASS-90xxxx` 是**通行证类物资 ID**。
> **数据表里的编号永远先当数据，不要当凭证。**

## §11 · 破解点定位：找「授权之后才存在的东西」

**错误的问法**：「卡密判断在哪，我 patch 它。」
**正确的问法**：「这程序要**先拿到什么**才肯进主程序？那个『什么』就是把手。」

| 授权模型 | 门在哪 | 把手在哪 |
|---|---|---|
| 纯本地判断（注册码算出来的） | 客户端 | 判断本身（patch 有效） |
| 联网强制握手 + 客户端布尔 | 客户端 native | **不能只关总开关**，要建立会话态 |
| 服务器下发授权后才有的载荷 | 服务端 | **下发的那个载荷**（客户端根本不判） |
| 云端下发 + 本地再校验 | 两边 | 下发物 + 校验的消费点 |

实测 VS 属于第三类且最干净：授权判断全在 `libjinverify.so`（15 个 `nativeCard*` JNI）+ 服务端；
客户端 Java 层没有本地判门（`LicenseInfo`/`VerifyConfig` 只是展示壳）→ **纯静态 patch APK 的 Java 层零效果**；
真正的把手是 `/api/v2/main-program-updates/check?variant=` —— 授权过了才给主程序。
→ 破解者做的事：把下发物**预先打包走私**，主程序编成 `offline` 版（`main()` 里硬编码 `"LOCAL-OFFLINE"`）。

**可迁移的三问**：
1. 这个程序**第一次碰网络**是为了拿什么？
2. 拿不到那样东西时，它会停在哪个界面/哪条日志？
3. 我能不能**自己把那样东西造出来**，而不是破解它的判断？

## §12 · 混淆判据（见两条就放弃 xref/图分析）

| # | 判据 | 怎么看 |
|---|---|---|
| 1 | **用运行时状态做种子** | `_ReadStatusReg(TPIDR_EL0)`（TID）、`rdtsc`、`gettimeofday`、`getpid` |
| 2 | **常量化成算术链** | `ROR/ROL + ADD 常数 + XOR 常数` 连环，常量搜索全落空 |
| 3 | **两级表查 + 间接分支** | `qword_T1[混淆索引] → qword_T2[结果] → BR xN` |
| 4 | **函数边界消失** | 反汇编器只找到几十个函数，且入口前一条不是 `ret` |

实测 VS 主程序 `main` 体四条全中（9MB `.text`，IDA 只认 14,075 个函数，几乎全是 `sub_XXXXXXXX`）。

**处置顺序**：① 放弃静态读懂，转 §9（第三方串）+ §10（数据表）出功能图；
② 要真读代码，把**跳转表**提出来做 handler 分类（判平坦化 vs 真 VM）；③ 平坦化可写 de-flatten，真 VM 只能提字节码。
**先判"平坦化 or VM"，再决定投不投入** —— 这个判断只需看表结构，不需要读懂一条指令。

## §13 · 取址纪律：任何「0 命中」先怀疑自己

```python
def v2o(v):
    for ph in LOAD_segments:
        if ph.vaddr <= v < ph.vaddr + ph.filesz:
            return ph.offset + (v - ph.vaddr)
```

两个真实案例：
- **vaddr 当 offset 直读**：`.data` vaddr `0xE62960` 直接按这个位置读 → **0 条物资**；
  实际 file off = `0xE56960`（delta `0xC000`）。修正后 **49,110 条**。
- **多字节编码误判**：第一次扫中文串得到 51,239 条"CJK"，几乎全是二进制误当 UTF-8；
  加上「NUL 分隔 + 字符白名单比例 ≥ 75%」两道过滤后剩 25 条，全都是真的。

> **判据：一个否定结论的成本，永远高于再验一次取址。**
> 尤其当这个结论正好**符合你当时的猜测**时——那才是最该怀疑自己的时候。

## §14 · 三条核心

1. **位置 > 算法。** 自解密动作永远是"解完跳到哪"，指纹是入口在段尾 + `DC CVAU/IC IVAU` + 写后跳。找位置，别猜算法。
2. **骨架 > 算法。** LZ 家族永远是"读位 → 进位分支 → 回引拷贝"。找骨架，就能自己写解码器。
3. **把手 > 判断。** 别问"卡密在哪判的"，问"授权过了才存在的那个东西是什么"。造那个东西，比改判断省一个数量级。

**止损**：不知道算法 + 没有能跑它的机器 + 解码器要写 2 小时以上 → **停手出定性结论**。
"卡在第几层、缺哪份输入"是有效结论；"差不多能脱"不是。
