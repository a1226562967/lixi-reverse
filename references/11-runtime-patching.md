# 运行时打桩与周期喂狗（加固无关）

> **加密/加固/VM 保护的是"怎么算"，从来不保护"谁被调用、返回值给谁"。**
> 只要在**函数边界**上动手，这套经验对下面这些形态全部通用 ——
> 无壳 / 压缩壳 / 函数级加密 / 全文件加密自解密 / VM 虚拟化 / OLLVM 平坦化 / 多态自修改。
>
> 实证：[[08-casebook.md]] 起源 3.1 —— **磁盘一个字节都没改**，12 个内存补丁解决问题；
> 破解者**明知目标里有 VM 却没去逆 VM**，因为 VM 只保护函数体，而他要的是"函数返回什么"。
>
> 配套脚本：`scripts\rkprobe.py`（五类打桩点静态侦察，15 秒扫完 67MB）。

---

## 零 · 为什么这套经验与加密形态无关

### 0.1 五个不变量（跨加密成立的原因）

不管目标用什么算法，下面五件事**必须**在运行期以明文形式存在，否则程序自己就跑不起来：

| # | 不变量 | 具体表现 | 对应的武器 |
|---|---|---|---|
| **I1** | **ABI 不变量** | 返回值在 `w0/x0`；out 参数是某个寄存器里的指针；bool 取值域是 {0, 非0} | **返回值打桩**（`mov w0,#imm; ret`） |
| **I2** | **调用图不变量** | 谁调用谁必须可解析：`bl` / PLT / vtable / `R_AARCH64_RELATIVE` | **PLT 桩打桩**、**虚表打桩** |
| **I3** | **值域不变量** | 判决结果只有有限几种取值（成功/失败/过期/时间戳/指针） | **out 参数伪造** |
| **I4** | **时序不变量** | 检测有周期、有超时、有心跳间隔 | **周期喂狗** |
| **I5** | **完整性不变量** | 校验的到底是"磁盘文件"还是"内存映像"还是"服务端记录" | **零修改原则** |

> 这五条不是某个样本的特例，是冯诺依曼机 + 操作系统 ABI 的固有属性。
> **所以"换一种加密"改变的只是难度，不改变可行性。**

### 0.2 加密只改变三件事

| 加密换了 | 变化的 | 不变的 |
|---|---|---|
| AES / RC4 / 换表 / 逐条密钥 | 静态**看不到**内容 | 入口还在、返回值还在 |
| 函数体加密（如 AndProtector） | 静态**看不到**函数体 | 入口跳板是明文 |
| VM / 平坦化 / 多态 | 静态**看不懂**控制流 | 边界（进入/返回）仍是 native ABI |
| 自解密 stub | 磁盘上是密文，内存里是明文 | **解密完成后**一切照旧 |

> 一句话记法：**加密把"中间过程"变黑，但把"两端"留白 —— 出口（返回值）和接口（调用关系）。**

## 一 · 五条找点判据（每条都能自动跑）

```powershell
python scripts\rkprobe.py <载荷 ELF> --json rk.json
```

一条命令同时输出下面五类；下面给判读。

### 判据 1 · 加密跳板（thunk）：入口被换掉了，但换法留下了指纹

```
sub  sp, sp, #0x10
str  x9, [sp]
ldr  w9, #<pc+4>        ← 从代码流里读一个 32 位常量（负数）
sxtw x9, w9
adr  x16, #<pc+4>
b    #<pc+8>
.word <负偏移>           ← 常量就嵌在代码里
add  x16, x16, x9        ← 算出表基址
ldr  x17, [x16, #8]      ← 相对偏移
add  x17, x17, x16
ldr  x9, [x16, #0x10]
add  x16, x16, x9        ← 密文块指针（每个函数不同）
ldr  x9, [sp]
add  sp, sp, #0x10
br   x17                 ← ① 打这里
```

**判读**：出现这个 20 指令模板说明加固器把"函数体"搬走了，但**函数入口仍是一段固定 native 代码**。
`br x17` 前面那 8 字节就是全体函数的"共同弱点"。

`rkprobe.py` 输出（起源实测）：

```
[1] 加密跳板 thunk: 199 处（br x17 模板）
    0x0380ed8c  score=3  TEXT(ent=6.18)      ← B1
    0x0381121c  score=3  TEXT(ent=6.24)      ← B2
    ...
```

> ⚠ **密文区里的 thunk 是随机噪声**：脚本给每个 thunk 算 ±2KB 局部熵，`ent>7.5` 标 `CIPHER?` 并排在后面。
> 起源 199 个 thunk 里只有 **161 个在明文区**，其余 38 个是 45MB 加密区里的假阳性。
> 同一条纪律也适用于 `elfprobe.py` 的引用密度（见 `04-elf-form-verdict.md` §四）。

**x86 等价物**：`push reg` + `mov reg, imm32` + `jmp reg` 的 thunk。

### 判据 2 · `.rela.plt` 是"全局机制的名单"

解析 `.rela.plt` → 得到"PLT 槽位 ↔ 导入函数名"全表。

起源实测（`rkprobe` 原样输出）：

```
[2] .rela.plt: 326 条，横切机制 20 条
    slot[29] GOT=0x4045838  alarm
    slot[77] GOT=0x40459b8  ptrace
    slot[96] GOT=0x4045a50  exit
    slot[139] GOT=0x4045ba8  fork
    slot[197] GOT=0x4045d78  abort
    slot[269] GOT=0x4045fb8  kill
    slot[325] GOT=0x4046178  dl_iterate_phdr
```

破解者把 `slot[29]`（alarm）的 PLT 桩改成 `mov w0,#0; ret` → **整个进程的 `alarm()` 变成 no-op**，
一次覆盖所有调用者，且不需要知道谁设了定时器。

**为什么通用**：`alarm`/`setitimer`/`ptrace`/`prctl`/`kill`/`exit` 这类横切机制一定走 PLT，一定有一张表。
**打表比追调用点便宜一个数量级。**

> 工具细节：`rkprobe` 输出的是 **GOT 槽地址**；要打的是 **PLT 桩代码地址** = `.plt` 节基址 + `idx*16`
> （起源：`slot[29]` → PLT 桩 `0x3fd2510`）。脚本已尽量补 `stub` 字段，无节表时按相邻差值推。

### 判据 3 · `.bss` 里的"单例标志" = 喂狗点

**特征**：
- 地址落在 `.bss`（`filesz=0` 的段里，无文件内容）
- 全量扫描只有 **2~5 处引用**（读一两处、写一处）
- 被读的地方通常紧跟条件跳转到"错误/退出路径"

起源实测（`rkprobe` 第一行就是它）：

```
[3] .bss 单例标志（2~8 处引用且有写）: 160 个
    0x04060cb4  reads=1 writes=1 sites=0x36cd77c:W, 0x36d140c:R
```

`FL = 0x4060cb4` 在 236 万条指令里只有 3 处引用 → 这是一个"违规标志"，读它的两个线程就是守护线程。

> **处置**：**不去改它**（改写入点会破坏栈 → 实测 SIGSEGV），改为**从外部每 10 秒写 0**。

### 判据 4 · 时间门的三种写法（都能一眼认出来）

| 写法 | 指令特征 | 起源实例 |
|---|---|---|
| 真实时间 | `mov w8,#0x71` + `svc #0`（ARM64 syscall 113 = `clock_gettime`），x0=0(REALTIME) | `0x38163ac`：读 `tv_sec` 后 `cmp now, deadline-1` |
| 单调计时 | `mrs xN, cntvct_el0` + `mrs xM, cntfrq_el0` | `0x38163e0`：`elapsed = cntvct - start`，`limit = count × freq` |
| 绝对死线 | 单独 `mrs cntvct_el0` 与内存里的时间戳比 | `0x381640c`：`cmp x9, [ctx+0x630]` |

`rkprobe` 输出：

```
[4] 时间门: 6 处
    0x03813afc  clock_gettime(113) 直接系统调用
    0x038163ac  clock_gettime(113) 直接系统调用     ← J1 的判定来源
    0x0398db68  cntvct_el0(单调计时/防回拨)
```

**处置分层**：
- 只看"是否超期"的判定 → 返回值打桩（`mov w0,#0`）
- 直接"超期就杀"的分支 → 分支消隐（`nop`）
- 有租约缓存/冻结需求 → 见 `05-server-verdict.md` 的时间冻结

> ⚠ **三条检查常常同时存在**（起源就是三条并列：J1/J2/J3）。
> 只打一条 = 另外两条照样杀你。**看到时间门必须把同一个函数里的全部分支一起数完。**

### 判据 5 · `R_AARCH64_RELATIVE → 跳板头` = 这是虚函数，有消费者

起源实测（`rkprobe` 4/4 命中）：

```
[5] R_AARCH64_RELATIVE -> 跳板: 163 条（虚函数/回调，有消费者）
    slot 0x405e170 -> 0x380ed54     ← 跳板头（不是 br 位置！）
    slot 0x405e1a0 -> 0x38111e4
    slot 0x405e1b8 -> 0x3811718
    slot 0x405f1f0 -> 0x387cd48
```

这些槽位落在 `.AnProtector.sdk` 段里。推论链：`R_AARCH64_RELATIVE` = 运行期填的绝对指针 → 指向跳板头 =
**函数指针** → 放在加固器段里 = **虚表/回调表** → 虚调用 → **全量 `bl` 扫描必然 0 命中**。

> **这条判据解决一个常见误判**：
> "我扫了全量 `bl`，没有任何地方调用这个函数，所以它是死代码/诱饵" —— **错**。
> 虚函数、函数指针、回调、`.init_array`、JNI 注册表都不产生 `bl`。先查 `.rela.dyn` 和 `data.rel.ro`。
>
> 脚本实现细节：RELATIVE 的 `r_addend` 指向**跳板起点**（`0x380ed54`），而 `br x17` 在跳板尾部（`0x380ed8c`）。
> 所以匹配要用**区间** `[start, br+4]`，不能用点比较。

## 二 · 四种打桩形态：怎么选

| 形态 | 字节（ARM64） | 什么时候用 | 风险 |
|---|---|---|---|
| **A. 返回值打桩** | `mov w0,#imm` + `ret`（8B） | 判定结果被当 bool/int 消费 | 最低。**首选** |
| **B. 分支消隐** | `nop`（4B，`1f 20 03 d5`） | "超期/失败就杀"的单条分支 | 低，但要**数全同族分支** |
| **C. 参数伪造** | `mov/movk` + `str` + `mov w0,#0` + `ret`（16B） | 函数有 out 参数（`int f(x0, T* out)`） | 中。字段/单位必须对齐 |
| **D. PLT / 虚表打桩** | 同 A，但目标是 `<.plt+idx*16>` | 横切机制（定时器、信号、清理） | 低，但覆盖面可能过宽 |

### 2.1 为什么"返回值打桩"优于"流程打桩"

`nop` 只能**跳过**，`mov w0,#imm; ret` 能**指定结果**：
- 跳过要求你懂这段控制流（后面还有什么、跳过去栈平不平）；
- 指定结果只要求你懂 ABI（返回值在哪个寄存器、调用者怎么用）。

起源 12 个点里 8 个是返回值/参数打桩，只有 3 个 `nop`、1 个 `ret`。

### 2.2 8 字节等长覆盖是硬要求

跳板的 `br x17` 是 4 字节，紧随其后的常是 4 字节数据/下一条指令。
`mov w0,#imm; ret` 正好 8 字节，**等长覆盖 = 不改任何地址、不重定位、不用考虑指令边界**。

> 变长覆盖会踩到：后续分支目标地址、`.eh_frame` 展开、指令对齐。

### 2.3 返回什么值？看调用者怎么消费

| 调用者模式 | 给什么值 | 起源实例 |
|---|---|---|
| `cbz w0` / `cmp w0,#0` 后走"成功"路径 | **0** | B1 / B4 |
| `cbnz w0` 后走"成功"路径（返回值是"有效"） | **1** | B3 / O1 |
| 返回值被 `cset w8, ne` 转 bool 再存 | 0 或 1（看下游） | `0x36cd798` |
| 返回值当"长度/句柄/指针" | **不能乱给**，要造合法值 | — |

> **最常见的翻车点**：把"返回 1 = 成功"的门改成了 0。
> **先读调用者，再决定值。** 判据：`cbz w0,<成功分支>` → 0 成功；`cbnz w0,<成功分支>` → 非 0 成功。

## 三 · 连"输出参数"一起伪造（最容易漏的一手）

### 3.1 教科书例子（起源 B2，observed）

```asm
; 原始
0x381121c  br x17                     ; 进加密函数（看不见实现）

; 补丁后（16 字节，正好覆盖跳板尾部）
0x381121c  mov  x8, #0xffff
0x3811220  movk x8, #0x7fff, lsl #16  ; x8 = 0x7FFFFFFF = 2147483647
0x3811224  str  x8, [x1]              ; ★ 写 x1 指向的 out 参数
0x3811228  mov  w0, #0
0x381122c  ret
```

可观察结果：UI 打印 **"登录成功，到期时间: 2038-01-19"**。
`0x7FFFFFFF` 秒 = 2038-01-19 03:14:07 UTC —— 一个 32 位有符号秒数的上限。

### 3.2 为什么必须连 out 参数一起写

只在返回值上打桩，会出现三种露馅：
1. 上层拿 `*out` 去格式化打印 → 显示真实（或垃圾）日期 → 用户/服务器都能看出不对；
2. `*out` 参与后续计算（比较、续期、写盘）→ 未初始化的栈值 → 崩溃或随机行为；
3. 有第二道检查"返回值成功但 out 为 0" → 直接判篡改。

### 3.3 三分钟识别"这个函数有没有 out 参数"

| 看什么 | 判据 |
|---|---|
| 函数入口后有没有 `str/strb/stp` 到 `[x1]`/`[x2]` | 有 → 出参 |
| 调用点后面有没有 `ldr x0,[sp,#N]` 再 `bl printf/format` | 有 → 那个缓冲是用户可见结果 |
| 返回值是 `int` 且 x1 在使用前没被读 | 强烈暗示 x1 是 out |
| 加固后的跳板 | **看不到**函数体 → 只能从调用点反推 |

> **通用做法**：先只打返回值，跑一次看现象。
> "过了但显示不对" → 补 out；"过了且显示合理" → out 不参与判定，可以不管。**观察比推理便宜。**

## 四 · 时序：用"输出门"分阶段，不要一次打完

### 4.1 起源的分段（observed）

```
等 stdout 出现 "驱动已链接"   → 打 J1/J2/J3 + R1/R2 + FL + O1（7 个点）
等 stdout 出现 "请输入卡密"   → 打 B1/B2/B3/B4/B5 + ST（6 个点）
往 fifo 喂任意 16 字符卡密    → 观察结果
```

### 4.2 为什么要分阶段（三条理由，与加密无关）

1. **求值时机**：每一批门只在对应阶段才被求值。提前打，会被后续初始化覆盖，或触发"值不合理"的自检。
2. **依赖顺序**：本例的 `Open()` 会遗留一个寄存器（`r8`）给后面的 SDK 初始化用。提前把 SDK 打桩，
   `r8` 就没了 → 后面崩。破解者 README 原文：`Do NOT RET SDK (need r8 from Open leftover / later)`。
3. **可观测性**：一次只改一批，出问题能定位到这一批。

### 4.3 同步点的选择（从便宜到贵）

| 同步点 | 成本 | 稳定性 |
|---|---|---|
| 目标自己打印的**提示语**（`grep` stdout） | 最低 | **高**（文案是产品的一部分，加固器不会去混淆它） |
| 进程存活/线程数变化 | 低 | 中 |
| 某个内存地址被写入（轮询） | 中 | 高 |
| 断点 / hook | 高（会暴露自身） | 低（反调试） |

> **提示语是最稳的同步点**，因为它属于"产品语义"。起源用 `grep -q "驱动已链接"` + 150ms 轮询 + 早死检测。

## 五 · 周期对抗：喂狗，而不是拆狗

### 5.1 实测结构（起源，`0x36cd770` 附近）

```asm
sleep(10)
if (FL != 0) goto error_path;      ; ← 违规标志被守护线程看到就死
sleep(20)                           ; ← README 说的 "20s watch"
rc = check(handle, 300);            ; 300 秒心跳校验
if (rc) { print(...); bl 0x3813c04; }   ; 失败 → 卡 5 分钟
sleep(30)
```

破解者做法：**每 10 秒把 FL 写 0**。

### 5.2 三条与加密无关的原则

1. **周期必须小于检测周期**，且留余量。本例 10s < 20s（2 倍余量）。
2. **不要改检测代码，改被检测的值**。改 `0x36d1404` 的写入点会破坏栈（实测 SIGSEGV）；改 `FL` 的值只影响数据。
3. **喂狗要幂等、要能并发**。多个守护线程可能同时读，写入必须原子（4 字节对齐 `str` 天然原子）。

### 5.3 什么时候该"拆狗"而不是"喂狗"

| 情况 | 选择 |
|---|---|
| 标志在可写数据段（`.bss`/`.data`）、外部能写 | **喂狗**（最安全） |
| 标志在只读段 / 被 mprotect 保护 | 只能改检测逻辑或改页属性 |
| 检测逻辑简单且无副作用（`if (flag) exit()`） | 可以把 `exit` 的调用点打桩 |
| 检测是"服务端心跳" | **都不能碰** —— 见 §七 |

## 六 · 工具纪律：怎么"碰"内存才不会被发现

### 6.1 用 `/proc/pid/mem`，不要用 ptrace

| 设计 | 为什么 |
|---|---|
| 走 `/proc/<pid>/mem`（或 `process_vm_writev`） | **不产生 `TracerPid`** —— `PTRACE_TRACEME` 检测、`/proc/self/status` 检测全部失效 |
| `patch` 命令带 `oldhex` | 打之前先比对原字节，打错了立刻暴露（而不是等程序崩） |
| 写后读回（`VERIFY_FAIL`） | 改完必须验证真的进去了 |
| `how_try=%s` 多路降级 | `/proc/mem` 被 SELinux 挡 → `process_vm_writev` → 其它路径 |

> **这是"运行时路线"能和反调试共存的关键**：大量反调试只检测 `ptrace`。
> **只要你不 attach，它就看不见你**。代价：拿不到寄存器/断点，只能"读内存 + 写内存 + 看 stdout"。

**最小工具骨架（C，交叉编译到 aarch64-linux-android，或直接照抄逻辑）**：

```c
// pm.c —— read/write/patch /proc/<pid>/mem。用法: pm patch <pid> <addr> <oldhex> <newhex>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>

static int rd(int fd, unsigned long a, void *b, size_t n) {
    if (lseek(fd, (off_t)a, SEEK_SET) < 0) return -1;
    return read(fd, b, n) == (ssize_t)n ? 0 : -1;
}
static int wr(int fd, unsigned long a, const void *b, size_t n) {
    if (lseek(fd, (off_t)a, SEEK_SET) < 0) return -1;
    return write(fd, b, n) == (ssize_t)n ? 0 : -1;
}
static size_t hex2bin(const char *h, unsigned char *o) {
    size_t n = strlen(h) / 2;
    for (size_t i = 0; i < n; i++) { unsigned v; sscanf(h + i * 2, "%2x", &v); o[i] = (unsigned char)v; }
    return n;
}
int main(int c, char **v) {
    if (c < 4) { fprintf(stderr, "usage: pm read|write|patch pid addr [hex] [hex]\n"); return 2; }
    char path[64]; snprintf(path, sizeof path, "/proc/%s/mem", v[2]);
    int fd = open(path, O_RDWR); if (fd < 0) { perror("open mem"); return 3; }
    unsigned long a = strtoul(v[3], 0, 16);
    if (!strcmp(v[1], "read")) {
        unsigned char b[256]; if (rd(fd, a, b, 16)) { perror("read"); return 4; }
        for (int i = 0; i < 16; i++) printf("%02x", b[i]); printf("\n"); return 0;
    }
    unsigned char nb[256]; size_t n = hex2bin(v[c - 1], nb);
    if (!strcmp(v[1], "patch")) {
        unsigned char ob[256]; size_t m = hex2bin(v[4], ob);
        unsigned char cur[256]; if (rd(fd, a, cur, m)) { perror("pre-read"); return 5; }
        if (memcmp(cur, ob, m)) { fprintf(stderr, "PRE_READ_FAIL (expect %s, got ", v[4]);
            for (size_t i = 0; i < m; i++) fprintf(stderr, "%02x", cur[i]); fprintf(stderr, ")\n"); return 6; }
    }
    if (wr(fd, a, nb, n)) { perror("write"); return 7; }
    unsigned char vb[256]; if (rd(fd, a, vb, n) || memcmp(vb, nb, n)) { fprintf(stderr, "VERIFY_FAIL\n"); return 8; }
    printf("WRITE_OK %lx %zu\n", a, n); return 0;
}
```

> 交叉编译：`aarch64-linux-gnu-gcc -static -O2 -o pm pm.c`（或用 NDK 的 clang）。
> 没有编译环境时，脚本里用 `dd of=/proc/<pid>/mem seek=...` 也能做单点，但没有 oldhex 校验。

### 6.2 选对进程（多进程/多开）

```sh
for p in $(pidof qiyuan.sh); do
  exe=$(readlink /proc/$p/exe) ; case "$exe" in *origin/qiyuan.sh) ;; *) continue;; esac
  sz=$(awk '/VmRSS/ {print $2; exit}' /proc/$p/status)
  [ "$sz" -gt "$BESTSZ" ] && { BESTSZ=$sz; PID=$p; }
done
```

> 外挂/游戏类进程常 fork 出多个同名进程（渲染、音频、子进程）。
> **打错进程 = 打空气 + 可能触发子进程的自检。**

### 6.3 基址要自己算，不要假设

```sh
grep 'r-xp.*qiyuan\.sh' /proc/$PID/maps | head -1     # 第一个 r-xp 段起点 = load base
target = BASE + 0x38163cc                              # PIE：所有静态偏移都要加基址
```

> Android busybox 没有 `bc` / 大数 `printf %x` → 需要纯 shell 的 64 位十六进制加法（分段 4 位相加带进位）。
> 或者干脆把基址加法放进 `pm` 工具里（`pm patch <pid> <base+off>`）。

## 七 · 负面清单（比"能改什么"更值钱）

起源的 README 一半篇幅是 `do NOT`（observed，原文摘录）：

| 动作 | 后果 | 原因 |
|---|---|---|
| `0x38139e8` 整函数 RET0 | **封号** | 它是 300s 心跳校验，服务器侧有独立判决，客户端不上报 = 异常 |
| `0x36d1404` RET（K40 机型） | **SIGSEGV** | 改写入点破坏栈/后续指令依赖 |
| 静态改磁盘 ELF | 驱动链接后 **SIGSEGV** | 进程会读自己的文件做一致性核对 |
| `Frida` 注入 | **封号** | 有 Frida 特征扫描 |
| 覆盖 2.5 版包 | **封号** | 版本号/包体被服务端记录 |
| RET `SDK/Notice/Version` 类桩 | 无效 | `Open` 遗留的 `r8` 被后续逻辑依赖 |

### 三条通用判据：什么时候"打桩"会被反杀

1. **服务端有独立判决** → 客户端打桩只改本地显示，服务器看到"心跳缺失/数据异常" → 封号。
   **识别**：抓包看有没有周期性上报；找 API 字符串。
2. **打桩点被后续逻辑依赖**（寄存器/栈/结构体字段）→ 崩。
   **识别**：打之前看这个函数的调用点后面**紧接着**读了什么。
3. **完整性校验覆盖"内存"而不只是磁盘** → 打桩会被发现。
   **识别**：找 CRC/哈希计算 + 覆盖范围（起源只校磁盘，所以内存安全）。

> **客户端能打桩 ≠ 服务端会认账。** 轻则功能异常，重则封号。
> 判断依据永远先看"这个判定有没有服务端副本"。

## 八 · 加密形态 × 经验可用性矩阵（本页最重要的一张表）

| 加密/加固形态 | 入口可见 | 返回值打桩 | 分支消隐 | PLT 打桩 | 喂狗 | 额外注意 |
|---|:--:|:--:|:--:|:--:|:--:|---|
| **无壳明文** | ✅ | ✅ | ✅ | ✅ | ✅ | 先查有无 CRC/签名 |
| **压缩壳 UPX/自解压** | 解压后 | ✅ | ✅ | ✅ | ✅ | 打桩要等自解压完成（输出门同步） |
| **函数级加密**（AndProtector） | ✅ 入口明文 | ✅ | ✅ | ✅ | ✅ | 打点在 `br x17`；函数体看不见不影响 |
| **全文件加密 + 自解密 stub** | 解密后 | ✅ | ✅ | ✅ | ✅ | 在解密**之后**打；偏移要加运行期基址 |
| **VM 虚拟化**（VMP / s5vmp / 自研） | ✅ 有 native 边界 | ✅ | ⚠ 慎重 | ✅ | ✅ | **只看边界不看 VM**；VM 内部 cmp 不要动 |
| **OLLVM 平坦化 / 指令替换** | ✅ | ✅ | ⚠ 需找支配点 | ✅ | ✅ | 分支可能被复制多份，要**数全** |
| **多态 / 自修改代码** | 每次布局不同 | ✅ | ✅ | ✅ | ✅ | 每次启动重算偏移，**禁止硬编码运行时地址** |
| **反调试（ptrace/Frida 检测）** | — | ✅ | ✅ | ✅ | ✅ | 用 `/proc/pid/mem`，**不要 attach** |
| **文件级 CRC / 签名校验** | — | ✅ | ✅ | ✅ | ✅ | **磁盘零改动**就天然通过 |
| **服务端签名判决**（Ed25519） | — | ❌ 无效 | ❌ | ❌ | ❌ | 只能 `05-server-verdict.md` 重放或跳过调用方 |
| **服务端心跳 + 封号** | — | ⚠ | ⚠ | ⚠ | ⚠ | 只改**本地显示侧**，保留真实上报 |

**读法**：只要目标**不是**最后两行，这套打法就成立。
最后两行不是"更强的加密"，是**判决不在客户端** —— 那属于另一个问题。

## 九 · 完整流程（Checklist）

```
0. 判层：判决在控制面 / 载荷面 / 特权面 / 服务端？
   → 如果是服务端：先走重放，不要浪费在打桩上

1. 静态先行（只看，不动）  ← python scripts\rkprobe.py <elf>
   □ 找跳板三件套(判据1)    → 得到"函数边界"清单（跳过密文区假阳性）
   □ 解 .rela.plt(判据2)    → 得到"横切机制"清单(alarm/ptrace/exit)
   □ 扫 .bss 单例标志(判据3) → 得到"喂狗点"
   □ 认时间门(判据4)        → 得到"到期/租约"分支全集
   □ 查 RELATIVE→跳板(判据5) → 确认虚函数/有消费者

2. 动态前提
   □ root + /proc/pid/mem 可写
   □ 确认磁盘零改动（不要 patch 文件）
   □ 选对进程（RSS + /proc/pid/exe 双重确认）
   □ 算出 load base（第一个 r-xp 段）

3. 分段打桩
   □ 等第一个输出门 → 打阶段 A
   □ 等第二个输出门 → 打阶段 B
   □ 每打一次：先比对 oldhex → 写 → 读回验证

4. 喂狗
   □ 周期 < 检测周期（建议 1/2）
   □ 写回原值（0）

5. 验收
   □ 主程序/功能真正可用（不是"日志对上了"）
   □ 活过一个检测周期以上（> 2× watch）
   □ 复查有没有封号迹象（服务端侧不可控）
```

## 十 · 局限（诚实边界）

1. **打桩看不见函数体** —— 不知道它内部还有没有别的检查。
   起源的 B1/B3/B4 到写完时仍只有"行为归类"，没有语义（函数体在加密区）。
   → "打了没效果"就是内部还有门，**只能靠行为观测逐个试**。
2. **服务端判决不可打桩** —— 架构边界，不是技术不够。
3. **喂狗是概率性的** —— 对抗的是"周期"；对方改成事件驱动（每次关键操作才检查）时失效。
4. **封号不可逆** —— 客户端全对也可能被服务端风控识别。**这一点在动手前就要接受。**

## 六.5 · 反制"反 hook"的唯一正确反应：**降层**

hook 被绕过时（打了没效果 / 被检测 / 返回值被改回去），不要在同一层反复试。按这条阶梯往下走：

```
Java/Kotlin 方法  →  JNI 边界（RegisterNatives 后的原生函数）  →  Native 内部函数
                 →  libc（open/read/recv/clock_gettime）      →  裸 syscall（svc #0）
```

| 现象 | 说明你被挡在 | 降到 |
|---|---|---|
| Frida/Xposed hook 无效、app 闪退 | Java 层有检测（`Thread.getStackTrace`、`Debug.isDebuggerConnected`） | JNI 原生函数（`jniprobe.py` 找注册表） |
| 原生 hook 打了但行为不变 | 有 inline hook 检测 / 校验函数头 | libc 调用点（`open/read/clock_gettime`） |
| libc hook 也无效 | 目标用了 **直接 syscall**（`svc #0`，不走 PLT） | 裸 syscall（改 `svc` 指令或 ptrace-free 内存改） |
| 连内存改都被还原 | 有守护线程周期性回写 | **喂狗**（改"被检测的值"）+ 降层到 syscall |

**判据**：
1. 每一层先确认"我的 hook 真的被调到了"（打一行日志），别假设生效；
2. 降到 libc 时**只 hook 你需要的那个调用**（`clock_gettime` 或 `read`），不要全量；
3. 到 syscall 层就用 `11` §六的 `/proc/pid/mem`（不 attach，不触发 ptrace 检测）。

> 实证：`08-casebook.md` 起源 3.1 —— 破解者在 Java/Native 层都被挡后，最终走的就是
> **`/proc/pid/mem` + 内存打桩 + 喂狗**（不动 hook，直接改内存）。
